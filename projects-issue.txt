ISSUE 1: Let the AI read the board back and edit a single shape
------------------------------------------------------------------------------
Source   : Comment on the X.com launch post.
Question : "Does it hand back the Excalidraw JSON or a rendered image? Getting
            the raw scene back is what made this useful for me, since the agent
            can tweak one box later instead of regenerating the whole thing and
            shuffling the layout."

Current behaviour
  - The AI tool sends a compact diagram spec (nodes + edges) via draw_diagram.
  - The server queues it in whiteboardData.pendingDiagrams.
  - The open browser tab converts it to Excalidraw elements (dagre layout) and
    draws it.
  - Nothing is ever returned to the AI: no scene JSON, no image.
  - There is no tool to read a board or to change one shape. Every
    draw_diagram call adds a NEW diagram to the right of existing content.

Problem
  To change one box the AI must draw the whole diagram again, which duplicates
  it and can change the layout.

Proposed work
  1. New MCP tool get_board_scene({ boardId })
       - Returns the saved Excalidraw elements (and optionally the original
         diagram spec) for a board the user owns.
       - Strip heavy fields (images/files) and cap the size of the response.
  2. New MCP tool update_diagram / edit_element
       - Edit by element id or by node id: change text, colour, size, delete
         a node or edge, add a node or edge.
       - Goes through the same pending queue so the open tab applies it, or
         edits the stored scene directly when the board is closed.
  3. Keep node ids stable
       - Store the original diagram spec (with node ids) next to the elements
         so later edits can target "node X" without moving the rest.
       - Re-run dagre only when asked, otherwise keep existing positions.
  4. Optional: export_board_image tool that returns a rendered PNG/SVG.

Things to decide
  - Return only the scene JSON, or also an image preview?
  - Edit while the tab is closed (server-side) or only through the queue?
  - Size limits for the returned scene.
  - Docs: update FLOWFORGE_GUIDE.txt section 6.3 (tools) and section 16
    (limits: "no board read / edit over MCP") when this ships.

Where to change
  - app/api/mcp/route.ts (new tools)
  - lib/ board queries (read scene by board id, scoped to the user's email)
  - db/schema.ts only if the diagram spec needs to be stored
  - features/workspace pending hooks (apply edit operations in the browser)

Status : DONE
         - get_board_scene (read the saved scene, with nodeId / diagramId / mode)
         - edit_board (update_text, set_color, delete; queued, applied in the browser)
         - get_diagram + revise_diagram (read one diagram as a spec, redraw it with
           steps added or removed; the browser replaces it in place, one undo step)
         Not done: add_node / add_edge / move / resize ops, export_board_image.

ISSUE 2: Let the in-app AI Helper edit existing shapes (not only create)
------------------------------------------------------------------------------
Source   : Follow-up to ISSUE 1 (MCP can now read and edit a board).

Current behaviour
  - The AI Helper (workspace-ai-floating-sidebar.tsx) only creates: it calls
    POST /api/ai/generate and always draws a NEW diagram on the canvas.
  - A user who wants to change one box can only ask for a new diagram, which
    duplicates the old one and can change the layout (same problem as MCP had).

Problem
  Users of FlowForge's own AI cannot say "rename this to Login" or "make the
  error boxes red" on shapes that are already on the board.

Already available (from ISSUE 1)
  - Shapes drawn by FlowForge carry customData { nodeId, diagramId }, also the
    ones drawn by the in-app AI (same diagramToElements function).
  - editOpSchema (update_text, set_color, delete) in features/workspace/schema.ts.
  - applyEdits() in features/workspace/ai/apply-edits.ts applies ops to the
    open canvas as one undoable step.

Proposed work
  1. Share the scene compaction logic
       - Move the element -> compact item logic out of getBoardScene
         (lib/boards.ts) into a pure function summarizeScene(elements), used by
         both the server and the browser.
  2. Edit prompt
       - New system prompt in features/workspace/ai/prompts.ts: given the
         compact scene, the selected ids and the user's request, return only
         { ops: EditOp[] }.
  3. Shared model helper
       - Extract the model fallback / timeout / error handling from
         app/api/ai/generate/route.ts into a lib/ helper so both AI routes use
         it (no copy-paste).
  4. New route POST /api/ai/edit
       - Clerk auth, zod body { prompt, scene, selectedIds }, Mistral returns
         { ops }, response validated with editOpSchema. Errors as { error }.
  5. Client
       - features/workspace/api: editDiagram; hook useEditDiagram (toasts in the
         hook, per CLAUDE.md). On success the component calls
         applyEdits(excalidrawApi, ops). No queue needed: the canvas is local.
  6. UI
       - Create | Edit tabs in the AI Helper popover. The Edit tab shows how
         many shapes are selected, has no mode picker, and a prompt box
         ("E.g. Rename this to Login, make it green").

Things to decide
  - UI: Create | Edit tabs in the popover (recommended) or a floating
    "Ask AI" button next to the selected shape.
  - Scope: send the whole board scene (recommended, allows "all error boxes")
    or only the selected shape (cheaper, but limited).
  - Hand-drawn / older shapes have null ids and cannot be edited. Optionally
    allow targeting by elementId in editOpSchema (also helps MCP). Hand-drawn
    labels are separate unbound text elements, so this needs extra logic.
  - Size limit for the scene sent to the model (same cap as get_board_scene).
  - Docs: mention in-app editing in FLOWFORGE_GUIDE.txt and README features.

Where to change
  - features/workspace/ai/ (summarizeScene, edit prompt)
  - lib/boards.ts (use summarizeScene)
  - lib/ (shared AI model helper)
  - app/api/ai/generate/route.ts (use the shared helper)
  - app/api/ai/edit/route.ts (new)
  - features/workspace/api, hook (editDiagram, useEditDiagram)
  - features/workspace/_components/workspace-ai-floating-sidebar.tsx (tabs)

Suggested branch : feat/ai-helper-edit

Status : DONE, shipped as the AI chat (see ISSUE 3) instead of Create | Edit tabs.
         The chat router decides between reply, create, edit and revise.
         POST /api/ai/edit was removed: the chat route calls generateEditOps itself.


------------------------------------------------------------------------------
ISSUE 3: AI chat with saved sessions per board
------------------------------------------------------------------------------
Source   : Follow-up to ISSUE 2. Users wanted to keep talking to the AI about a
           diagram (update it, ask for more detail) and see the conversation.

Behaviour
  - The AI button opens a chat (features/workspace/_components/chat/*). Each
    message goes to POST /api/ai/chat; a router model decides:
      reply   -> text only
      create  -> client calls POST /api/ai/generate and draws a new diagram
      edit    -> server returns edit ops, client applies them (applyEdits)
      revise  -> client rebuilds the diagram's spec from the canvas and calls
                 POST /api/ai/revise, then lays it out again (dagre) and replaces
                 the old diagram in place (one undoable step)
  - Optional diagram type icons under the message box are a hint for new diagrams.
  - Sessions: tables chatSessions + chatMessages. APIs under /api/ai/chat-sessions
    (list, rename, delete, paged messages, correct an assistant message).
    Session name = first ~40 characters of the first message. History sent to the
    model = last 12 messages of the session. The first message creates the session.
  - UI: start screen, conversation (older messages load on scroll up), session
    list, three-dots menu (rename, session list, delete with confirmation), the
    popover only closes with X / the AI button / Escape, and the open session is
    kept in the URL (?session=<id>) so a reload reopens it.
  - Saving: session + turn are written in one db.batch after the model answered.
    If the canvas step fails afterwards, the saved assistant message is rewritten.

Known limits
  - Web / mobile mockups cannot be revised (they are spatial layouts).
  - Revise re-lays out the whole diagram: manual moves and detached arrows are lost.
  - Hand-drawn shapes have no ids, so the AI cannot edit them.
  - The scene sent to the router is capped at 300 FlowForge shapes.

Status : DONE
